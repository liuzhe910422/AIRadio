# AIRadio：AI 全流程研发实践与工程证据

## 1. 本团队的 AI 研发实践

本团队在 AIRadio 的开发中，全程使用 AI 辅助代码编写、问题调试和各次 PR 实现。我们将 AI 融入功能实现、验证与迭代，也将语音模型能力接入产品工作流程。

我们基于 XiaoZhi／ESP-IDF 等开源工程和第三方依赖开展研发。本项目新增与修改工作均在 AI 帮助下完成；本团队负责目标设定、工程约束、实机操作、问题反馈和最终验收，上游底座与依赖沿用各自的开源成果。

我们通过 `github/pr_*.md` 记录每次变更的范围、验证结果和限制，使用 OpenSpec、代码与测试串联需求、设计和实现。本文引用这些过程材料介绍团队的研发方法与工程产出；PR 文档保留各次变更当时的记录。

## 3. 可复用的研发流程

本团队采用以下研发流程：

1. **明确任务与边界**：给出用户目标、涉及层次、不能改的行为及验收条件；依赖现有框架实现，避免改造整个底座。
2. **提供相关上下文**：让 AI 阅读最近实现、协议、板卡限制、日志和错误输出，而不是只描述“不能用”。
3. **形成有限范围的方案**：确认状态、消息、线程及资源所有权；复杂任务先拆成可验收步骤。
4. **实施与验证**：AI 协助修改代码、编写测试、运行编译和检查；人在需要时执行刷机、触摸和声音验收。
5. **将失败反馈给 AI**：提供复现步骤、固件日志、服务端事件和现象，沿假设定位、修复，再检查正常及异常路径。
6. **留下可审查结果**：记录修改范围、验证命令、结果和限制，形成 PR 过程材料。

以下案例整理了我们使用 AI 完成跨层实现与问题调试的过程，相关技术细节可通过 PR 记录与代码查阅。

## 4. 案例一：从整段录音到实时半双工

**任务**：改善“录完再发”的交互，使编码后的音频可以逐帧转发和播放。

**工程产出**：独立 WebSocket 传输 16 kHz、单声道、60 ms Opus 帧；发送队列、接收抖动缓冲、录音与网络任务分工，以及音频输入和取消路径的并发处理。工作横跨固件音频、设备界面和服务端协议，体现 AI 在跨层实现中的参与。

**过程材料**：[实时半双工 PR](../github/pr_realtime_intercom.md)、[后续稳定性 PR](../github/pr_intercom_current_branch.md)。前者记录服务端测试通过，但当时尚未完成固件编译和实机验证；后续记录包含进一步的实机日志验证。当前行为以[总体设计](intercom-overview.md)和代码为准，不能将历史 X 按钮等旧交互当成当前界面。

**团队实践**：我们将实时对讲拆分为采集编码、网络发送、接收缓冲和播放等环节，通过连续多轮对讲检查状态恢复与播放效果。

## 5. 案例二：AI 辅助定位“说话中”无法结束

**现象**：突发收包使接收缓冲溢出后，设备一直显示“说话中”。

**原因链**：溢出路径清空 `incoming_id_`，却仍处于播放状态；后续 `end` 因 ID 不匹配被忽略，超时逻辑也失去识别当前会话的依据。

**修复**：保留当前消息 ID，用 `incoming_overflowed_` 标记丢弃该段后续音频，继续接受匹配的 `end/abort` 并完成收尾；断线时也清理标记。修复目标是恢复会话生命周期，不是增加缓冲或保证溢出音频完整。

**证据**：[修复说明](../github/pr_intercom_receive_overflow.md)、[固件实现](../main/intercom/intercom.cc)、[状态定义](../main/intercom/intercom.h)。PR 记载 ESP-IDF v6.0.2 下目标板编译通过；该 PR 未新增自动回归测试，溢出、超时、断线与下一轮对讲仍需专项实机验收。

**团队实践**：我们将异常现象、状态变化和日志反馈给 AI，沿“现象 → 状态和日志 → 原因 → 修复 → 验证”的过程定位问题，使修复保持在会话收尾的职责范围内。

## 6. 案例三：托管从模型调用走向可控产品

**任务**：让在线设备在真人消息之后按上下文决定是否回复，同时避免自动对话循环、过期回复和打断真人。

**工程产出**：结构化 `should_reply/text` 决策、有界任务队列、设备与房间视图及托管代次校验、退出后丢弃旧结果、自动消息过滤，并通过现有 TTS 与 Opus 链路播放。

**证据**：[托管 PR](../github/pr_intercom_hosting.md)、[托管实现](../server/hosting.go)、[测试](../server/hosting_test.go)。`TestHostingDecision` 校验适配器处理结构化响应，`TestHostingScopeAndCancellation` 校验托管退出后的任务失效和自动消息防循环。测试不等于模型真实回答质量评测。

PR 记录 Go race 回归、真实模型适配调用及固件编译结果，同时明确当时仍需端到端实机验收。真实调用仅证明一次接口适配成功，不证明整体准确率；不能将 mock 测试说成真实模型或实机测试。

**团队实践**：我们使用 AI 协助实现模型接口，也同步处理任务失效、自动消息过滤和真人优先等控制逻辑，使模型能力与设备运行规则衔接。

## 8. 过程记录与持续改进

我们通过 PR 文档、设计任务和测试记录保留实现与调试过程。后续将继续补充脱敏的需求、关键诊断和工具输出，便于复盘具体问题如何解决。

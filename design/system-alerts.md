# 系统告警设计与当前实现

状态：已实现服务端调度、设备采集、视觉判断、温湿度判断、房间通知和告警记录；核对日期 2026-10-31。服务端 Go 编译检查已通过，ESP32-S3 设备端仍需按实际固件版本完成编译和硬件回归。

## 1. 功能范围

系统告警由服务端定时触发，不依赖小智 MCP 会话。当前固定提供三份全局配置：温度告警、湿度告警和视觉告警。每种类型只有一条配置，配置修改后对后续采集立即生效。

每份配置包含：启用状态、目标房间、指定采集设备、采集周期、通知文字和是否发送 TTS。温度和湿度分别配置一个高于或低于阈值；视觉配置使用独立提示词，并复用托管 LLM 的 URL、模型和 API Key。

控制台的“系统告警”页包含“温度”“湿度”“视觉”“告警记录”四个页签。房间和设备从现有管理接口加载为下拉选项，保存时服务端再次校验它们存在。设备必须在线且仍属于目标房间才会执行采集；不会自动改用其它设备。

## 2. 数据流

```text
告警配置
  -> 服务端周期调度
  -> 指定设备 Intercom WebSocket 控制帧
  -> 设备采集传感器或摄像头
  -> 设备返回结构化读数或图片 URL
  -> 服务端判断阈值 / 调用托管视觉 LLM
  -> 命中后保存记录、广播图片（视觉）、发送文字和 TTS
```

告警当前不做恢复状态、去重或冷却合并。每次定时采集命中条件都会产生一条记录并通知。

## 3. 设备采集协议

服务端向指定设备发送：

```json
{"type":"alert_capture_request","request_id":"...","content":"sensor"}
```

或：

```json
{"type":"alert_capture_request","request_id":"...","content":"image"}
```

设备返回：

```json
{"type":"alert_capture_response","request_id":"...","ok":true,"temperature":24.3,"humidity":63.0}
```

视觉采集返回图片 URL：

```json
{"type":"alert_capture_response","request_id":"...","ok":true,"image_url":"/api/intercom/images/<id>"}
```

设备端在 `Intercom::OnData()` 中处理请求。传感器读取使用板级 DHT11 快照；视觉采集直接调用摄像头、JPEG 编码和现有图片上传接口，不经过 `self.camera.take_photo` MCP 工具。

设备端对告警拍照和 JPEG 编码使用互斥，避免并发捕获。当前 JPEG 编码质量为 60，并限制编码输出缓冲；图片显示仍会申请 RGB565 解码缓冲，连续图片会产生较高 PSRAM 峰值，设备需要限制图片记录数量并观察最大连续内存块。

## 4. 温度和湿度告警

服务端收到结构化读数后，只判断对应类型配置的阈值：

- 温度告警：温度高于或低于配置值时命中；
- 湿度告警：湿度高于或低于配置值时命中。

命中后向目标房间在线设备发送系统聊天文字；启用 TTS 且 TTS 配置有效时，将相同文字加入现有 TTS 队列。告警记录保存房间、设备、实际值、阈值、时间和通知文字。

## 5. 视觉告警

服务端先下载设备上传的 JPEG，并保存到：

```text
server/recordings/pic/
```

然后将图片转为：

```text
data:image/jpeg;base64,...
```

通过托管 LLM 的 OpenAI 兼容 `chat/completions` 接口发送。视觉提示词独立保存，不复用托管助手的普通文本提示词。默认提示词要求检测真实火焰以及电脑、手机、平板、电视或显示器中显示的火焰图片、视频和缩略图；命中返回 `alert=true`。

只有 VLLM 返回 `alert=true` 时，服务端才会：

1. 向目标房间广播 `image_message`，控制帧只携带图片 URL；
2. 写入视觉告警记录；
3. 发送文字系统消息；
4. 按配置发送 TTS。

VLLM 请求失败、HTTP 非 2xx、响应 JSON 无效或未返回 `alert=true` 时，不广播图片、不发送告警文字，也不写入命中记录。服务端会记录实际提示词、HTTP 状态、原始响应和最终判断，便于排查模型输出。

## 6. 服务端接口和存储

- `GET /api/alerts`：读取三种告警配置；增加查询参数 `records=1` 时返回告警记录。
- `PUT /api/alerts`：按 `type` 保存固定配置，类型为 `temperature`、`humidity` 或 `vision`。
- `GET /api/alerts/{type}`：读取单种配置。
- `DELETE /api/alerts/{type}`：删除配置（服务启动时会重新补齐三种默认配置）。

配置和记录存储在 SQLite 的 `service_config` 表 `alerts` 项中，结构为：

```json
{"rules":[...],"records":[...]}
```

告警记录最多保留 500 条。图片文件和服务端内存图片 URL 的生命周期仍是独立的；当前 HTTP 图片存储适用于可信内网联调，服务重启后内存图片 URL 会失效，但 `recordings/pic` 中的采集文件保留。

## 7. 设备显示和资源限制

命中的视觉图片沿用普通 `image_message` 处理：设备下载 URL、解码缩略图并放入对讲记录，点击可查看大图。图片解码后的 RGB565 缓冲约为 800×600×2 字节，叠加 JPEG 原文、编码缓冲、音频和 LVGL 资源会造成 PSRAM 峰值。连续图片过多可能导致 JPEG 编码或解码失败；需要限制设备端图片记录数量，不能把图片数量和普通文字记录数量简单等同。

## 8. 验证

服务端可用浏览器模拟器验证温湿度采集响应；视觉链路需要真实摄像头设备。应检查：指定设备和房间匹配、设备离线超时、JPEG 上传、图片文件保存、VLLM 原始响应和最终布尔判断、命中后的图片广播/文字/TTS，以及连续采集期间的 SRAM/PSRAM `free` 和 `largest` 指标。

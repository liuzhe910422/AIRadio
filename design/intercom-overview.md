# 灵矽 AI 对讲总体设计

状态：按当前代码整理，核对日期 2026-10-24。接口细节见[协议](intercom-protocol.md)，早期链路范围见[第一版设计](intercom-v1.md)。`github/pr_*.md` 是各次变更的历史记录，不代表最新实现或本次重新验证结果。

## 1. 产品与当前能力

项目基于小智固件实现 AI 对讲机，面向车队、调度和临时协作。目前主要适配 Waveshare ESP32-S3 Touch LCD 3.5B，使用 480×320 横屏。用户点击大按钮开始实时对讲，再次点击结束；房间操作主要通过灵矽（小智）语音通道提供的 MCP 工具完成。

| 能力 | 当前实现 |
| --- | --- |
| 实时半双工对讲 | 独立 WebSocket 逐帧发送 Opus，同房间转发；全局同时只允许一段语音 |
| 房间管理 | 默认房间、创建、四位加入码（1000～9999）、加入／退出、邀请接受、编辑和软关闭 |
| 控制台 | 动态用户管理、设备总览、持久化模拟设备、浏览器 Opus 对讲及语音服务配置 |
| 会话记录 | 百炼 ASR 异步识别，设备最多保留20条，支持点击回放 |
| 系统通报 | 上线、加入和邀请文字通知，可通过百炼 TTS 自动播报 |
| 聊天总结 | MCP 返回本机保留的识别文字，由小智生成总结 |
| 托管代答 | 真人 ASR 完成后由千问判断是否回复，再通过 TTS 在房间播放 |

当前未实现设备绑定控制台账号、多组织／角色隔离、设备 token、永久聊天历史、离线补播或跨实例路由。开发模式已支持可选共享对讲 API Key，新 WebSocket 连接在 hello 时校验。

## 2. 系统职责

```text
                          灵矽／小智语音通道
                       （自然语言、MCP、OTA）
                                  ^
                                  | 直接连接
AIRadio 终端（固件 MCP、屏幕、大按钮） <----> 独立 Go 对讲服务 <----> 同房间在线设备
       |                                      |\
       |                                      | HTTP 控制台／SQLite
       |                                      | ASR／TTS／托管 LLM
       +---------- WebSocket / Opus ----------+
```

架构边界需要特别明确：**AIRadio 终端直接连接灵矽（小智）语音通道完成语音交互和 MCP 工具调用，不经过 Intercom Service；Intercom Service 只负责设备之间的实时对讲、房间与成员、临时记录和 AI 服务调度。** 小智助手会话与对讲 WebSocket 独立，结束一次助手会话不会断开对讲连接。固件 `main/intercom/` 负责对讲连接、房间状态、录放音协调和临时记录；`Application` 统一调度应用状态，`AudioService` 提供共享音频能力；3.5B 显示层只展示状态并提交操作。

Go 服务在同一进程提供管理 HTTP API、设备控制与音频转发。ASR、TTS 和托管 LLM 使用独立有界任务队列，失败不应阻塞实时对讲；第三方密钥只在服务端使用。详细实现见[ASR 与会话记录](intercom-asr-session-chat.md)、[托管模式](intercom-hosting.md)。产品展示页和架构图见仓库根目录 README 与 [`homeweb/`](../homeweb/)。

## 3. 身份、账户与持久化

设备在 Wi-Fi 高级设置中配置独立的 `intercom.device_id` 和 `intercom.server_url` NVS 项，不改写 `board.uuid` 或小智连接配置。设备 ID 由客户端自报，用于路由和邀请判断；`device_type` 的 physical／simulator 也属于自报属性。

控制台账号支持动态创建、列表查询和密码重置，所有登录用户具有相同管理功能，没有按用户划分的设备或房间。新数据库初始账号为 `admin/admin123`；已有数据库从旧 admin 表迁移，不覆盖已有 users 密码。指定 `-db` 时持久化账号、设备、房间和服务配置，无数据库模式只在内存保存。

控制台使用12小时随机 Cookie 会话，刷新页面可恢复有效登录；退出撤销当前会话，重置任意用户密码撤销全部会话，服务重启后需重新登录。当前不提供删除用户或公开注册。操作和接口见[第二版设计](intercom-v2.md)及[协议用户管理](intercom-protocol.md#13-控制台用户管理)。

## 4. 房间与语音操作

新设备进入固定默认房间；已有设备恢复保存的活动房间，关闭的房间回退默认房间。一台设备同时只有一个活动房间。普通房间有稳定 ID 和固定四位数字加入码（1000～9999，不使用前导零），名称可修改、可重名。

创建者自动加入；邀请列表为空表示开放加入，非空时仅创建者和受邀设备可以加入。在线受邀设备收到通知后自行接受，不自动移动。修改邀请范围不移除已有成员。关闭房间使成员返回默认房间，并中止该房间的音频、清空在线成员旧视图及托管状态。

固件提供九个普通 MCP 工具：房间查询／创建／加入／退出／接受最近邀请、会话文字查询、托管设置及查询。按名称加入时，小智可先调用 `list_rooms`，唯一匹配后使用字符串加入码；同名时应追问。没有独立的 `switch_room` 工具。3.5B查询列表后提供15秒倒计时触摸选房弹窗，显示名称与加入码，点击申请切换并等待服务端确认。

列表工具等待实际服务端响应，最多5秒；接受邀请不需要输入邀请码，使用最近一次通知保存的加入码；创建、加入、退出、接受邀请和托管设置只返回请求发送或排队结果，不能据此声称业务已成功。设备状态以服务端确认更新。详见[MCP 实现](intercom-mcp-implementation.md)。

## 5. 音频与消息生命周期

麦克风 → 16kHz 单声道、60ms Opus → 有界发送队列 → 对讲 WebSocket → 同房间接收设备 → 约8帧抖动缓冲 → 解码播放。每条 Binary 消息恰好承载一个原始 Opus 包，控制帧使用 JSON。服务端在 start 时固定房间，默认立即转发，不等待 receive_ready；忙碌接收者可拒绝本段。

固件最多录制30秒，单段最多500帧、512KiB，单帧最多4096字节；服务端另有35秒会话截止。全局发言锁仍会让不同房间互相等待，不支持跨房间并行发言。end_ack 仅确认服务端接收／排队情况，不保证扬声器播放完成。

完整语音结束后生成临时聊天记录并异步识别，发送者也收到记录。音频和文字保存在服务内存；音频最长30分钟，全局32MiB及512条记录上限。设备最近20条记录包含系统通知，切房或断线清空，不补拉历史。回放使用 AIR1 包流；独立调试 WAV 受 `-save-wav` 控制，不是聊天回放存储。

## 6. 设备交互与音频协调

3.5B 左侧显示房间、对讲状态、大按钮和小智回复；右侧显示可滚动的彩色文字记录。普通模式按钮蓝色，托管模式黄色，点击托管按钮请求退出。顶部显示配置的本机对讲设备ID，未配置时提示未配置；未展示实时电量、网络指标或在线成员数。

助手、录音、接收和回放共用音频硬件，由应用任务协调互斥。实时对讲可抢占记录回放，真人发言可中止托管自动回复。LVGL 和网络回调只提交工作，主设备状态通过 `Application::SetDeviceState()` 修改；队列与缓存必须有界。BOOT 键保留助手操作。

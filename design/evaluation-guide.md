三天赛制下优先用连续任务演示、工程记录和可复算假设支撑答辩。新增材料是证据整理与验收方案，不代表已完成客户试点或本次重新执行硬件测试。

灵矽 AIRadio 是基于灵矽／小智语音通道和 ESP32 固件构建的行业 AI 对讲方案，面向车队、物流园区、仓储和临时协作现场。

现场人员经常需要驾驶、搬运或操作设备，双手无法持续操作手机或复杂菜单。AIRadio 将三类交互放在同一条工作链路中：

- **即时沟通**：用大按钮开始和结束对讲，优先保证发言确定性和实时性。
- **复杂操作**：用自然语言查询房间、创建或加入协作空间、接受邀请以及切换模式。
- **智能协助**：在线托管设备结合近期对讲上下文按需代答，并支持语音转写、回放和总结。

产品主页：[http://154.94.238.56/](http://154.94.238.56/)。主页当前使用 HTTP，浏览器出现安全提示时，请确认地址后选择继续访问。项目介绍视频见 README 中的下载链接。

## 2. 评审快速体验路径

建议按以下顺序演示，完整路径约 3～5 分钟：

1. 打开产品主页，说明司机、仓储和现场作业人员双手繁忙的使用场景。
2. 在首屏点击大按钮，展示开始发言和结束发言，说明按钮用于低延迟、确定性的即时动作。
3. 进入交互演示的“切换协作空间”，展示语音查询房间列表并选择房间。
4. 进入“AI 托管”，打开托管开关，展示真人消息、上下文判断和 AI 语音回复的关系。
5. 进入“消息回顾”，展示转写、回放和对讲总结。
6. 在实机照片区域切换待机、说话中、转写、托管和选房状态，说明网页演示对应当前设备界面。

主页交互为静态演示，不录音、不连接真实设备；真实链路由 `server/` 和固件实现。

## 3. 核心技术亮点

### 即时链路与智能链路解耦

终端直接连接灵矽（小智）语音通道执行自然语言理解和 MCP 工具调用。终端通过独立的 Intercom WebSocket 连接完成设备间对讲。ASR、TTS 和托管 LLM 使用异步有界任务队列，不让外部 AI 服务阻塞实时音频转发。

### 确定性交互与自然语言互补

即时发言使用大按钮，避免等待唤醒词、语音识别或模型工具选择；房间管理和模式切换使用语音，减少多层菜单操作。这是针对现场工作节奏的交互分工，而不是追求所有动作都由语音触发。

### AI 托管的安全边界

托管只处理真人完成 ASR 的消息，不处理系统通知或自动回复，避免模型自循环。任务带有设备、房间视图和托管代次校验；退出托管、切房、断线后，旧任务结果会被丢弃。真人发言优先，自动语音可以被中止。

### 可回顾的短期上下文

对讲结束后异步识别文字，设备保留近期记录并支持点击回放。会话总结只读取当前设备保留的已识别文字，并明确提示记录范围，不把临时对讲包装成永久历史。

## 4. 系统架构

<p align="center"><img src="../homeweb/assets/airadio-architecture.svg" alt="AIRadio 系统架构" width="900"></p>

- **AIRadio 终端**：`main/intercom/` 管理设备 ID、房间状态、录放音协调、临时记录和 MCP 工具；当前主要适配 Waveshare ESP32-S3 Touch LCD 3.5B。
- **灵矽语音通道**：终端直接连接，用于自然语言理解、MCP 工具调用和小智助手交互。
- **Intercom Service**：`server/` 使用 Go 提供房间和成员管理、WebSocket / Opus 音频转发、会话记录、控制台和 AI 任务调度。
- **AI 服务**：ASR 生成文字，TTS 播报通知和托管回复，Hosting LLM 判断托管设备是否需要回复。

音频路径：

```text
麦克风 → 16 kHz 单声道 Opus → Intercom WebSocket
      → 同房间设备 → 抖动缓冲 → 解码播放
```

智能路径：

```text
完整对讲 → ASR → 近期消息上下文 → Hosting LLM 判断
         → TTS → Opus → 房间播放
```

## 5. 设计取舍

| 设计选择 | 适用价值 | 当前边界与扩展方向 |
|---|---|---|
| SQLite 持久化 | 单机或单园区部署不需要额外数据库服务，依赖少、备份简单、运维成本低 | 后续可将存储层替换为 PostgreSQL 等集中式数据库 |
| 半双工 + 全局发言权 | 符合传统行业对讲习惯，避免多人同时发言导致声音混杂 | 当前不同房间也共享发言锁，跨房间并行可作为后续扩展 |
| Opus 逐帧传输 | 在嵌入式设备和现场网络中节省带宽，支持有界队列和逐帧播放 | 当前不做音频重传和离线补播 |
| 近期记录而非永久历史 | 控制设备内存、服务端缓存和隐私暴露范围，适合临时现场沟通 | 后续可增加管理员可控的历史存储策略 |
| 在线 AI 托管 | 使用最新房间上下文即时判断，避免离线时产生过期回复 | 当前要求设备在线，未实现离线代答和长期记忆 |
| 大按钮 + 语音双通道 | 同时兼顾发言实时性和房间管理便利性 | 仍可继续扩展免手操作和更多语音工具 |
| 单体 Go 服务 | 房间、音频、控制台和 AI 队列部署简单，适合单车队或单园区快速落地 | 后续可拆分服务并增加跨实例路由 |

这些选择以目标场景为前提。它们降低了首次部署和现场使用的复杂度，同时保留了清晰的服务边界和后续替换空间。

## 6. 工程可靠性

- 音频发送、接收、ASR、TTS 和托管任务均使用有界队列或明确大小限制。
- 实时音频转发不等待外部 ASR、TTS 或 LLM 请求。
- 托管任务具备超时、冷却、过期、断线、切房和退出取消检查。
- 自动回复标记为 `automated`，不会再次进入 ASR 和托管判断，防止循环。
- 设备端记录最多保留 20 条，服务端临时音频和消息缓存有容量上限。
- API Key 不在配置查询响应中回显，配置可通过 SQLite 持久化。
- MCP 修改类工具返回排队或请求发送结果，最终状态以服务端确认事件为准。

## 7. 可复现入口

启动对讲服务：

```sh
cd server
go run . -listen 127.0.0.1:9200 -db ./data/intercom.db
```

列出固件构建目标：

```sh
python3 scripts/build.py --list-boards
```

构建当前主要目标时，使用 `--list-boards` 输出的准确板卡和变体名称。项目要求 ESP-IDF v6.0.1 或更高版本，推荐 `release/v6.1`。

主页本地预览：

```sh
cd homeweb
python3 -m http.server 8765 --bind 127.0.0.1
```

## 9. 评审结论参考

AIRadio 的核心价值不只是把语音模型接到硬件上，而是围绕行业现场重新分配交互职责：把最需要实时性的动作做成大按钮，把复杂的房间操作交给自然语言，把无法及时响应的沟通交给带上下文的 AI 托管，并把短暂的语音变成可回顾的信息。SQLite、单体服务、半双工和短期记录都是服务于当前落地场景的工程取舍，而不是未定义的技术缺口。
